# 1. Bugs

## SEC-01 · Unauthenticated system-prompt override with no length cap

| Attribute    | Detail                                                                                                      |
| :----------- | :---------------------------------------------------------------------------------------------------------- |
| **Category** | Security / Cost                                                                                             |
| **Severity** | **Critical**                                                                                                |
| **Location** | `server/schemas/chat.py:24`, `server/routes/chat_routes.py:36-49`, `server/services/bedrock_service.py:134` |

**The "Why".** `ChatStreamRequest.system_prompt` is an optional, **unvalidated, unbounded** string that any anonymous caller may set, and it is passed straight to Bedrock:

```python
# schemas/chat.py:24
system_prompt: Optional[str] = Field(None, description="Custom system prompt override")
# bedrock_service.py:134
active_system_prompt = system_prompt or DEFAULT_SYSTEM_PROMPT
```

Two consequences:

1. **The portfolio persona is optional.** Anyone can replace it and use the site's AWS account as a free general-purpose LLM.
2. **Cost amplification.** The only ceiling is `MAX_BODY_BYTES` (1 MB). `CHAT_FREE_MESSAGE_LIMIT` counts _user-role messages_, so a single request with one short user message and a ~1 MB system prompt passes every check. At ~250 k input tokens per request, with `CHAT_MAX_CONCURRENCY=4` and a ~3 s round trip, a single IP can sustain roughly **20 M input tokens/minute**. The general rate limit is 60 req/min per IP and `/chat` is _not_ on the strict auth budget (SEC-04).

**The Fix.** Drop the field, or gate it behind auth and cap everything:

```python
class ChatStreamRequest(BaseModel):
    messages: List[ChatMessage] = Field(..., min_length=1, max_length=40)
    conversation_id: Optional[str] = Field(None, max_length=36)
    model_id: Optional[str] = Field(None, max_length=128)
    stream: Optional[bool] = True
    # system_prompt removed — the server owns the persona.

class ChatMessage(BaseModel):
    role: Literal["user", "assistant"]
    content: str = Field(..., max_length=8_000)
```

Then lower `MAX_BODY_BYTES` for `/chat` specifically (64 KB is generous), and add a per-IP daily token budget backed by the same counter store as the rate limiter. This is the single highest-value fix in the report and it is a ~20-line change.

## BUG-01 · One unknown event type destroys the whole analytics batch

| Attribute    | Detail                                                                                        |
| :----------- | :-------------------------------------------------------------------------------------------- |
| **Category** | Bug / Data loss                                                                               |
| **Severity** | **High**                                                                                      |
| **Location** | `frontend/js/form.js:156`, `server/schemas/event.py:7-16`, `frontend/js/analytics.js:319-341` |

**The "Why".** `form.js:156` emits `trackEvent("contact_prompt", …)`. The server's `EventTypeName` `Literal` accepts seven types and `contact_prompt` is not among them. Because `BulkEventCreate` validates the whole list, one bad element fails the request. Executed against the real schema:

```
REJECTED -> FastAPI returns 422 for the WHOLE batch
  errors: 1 | offending index: ('events', 1, 'event_type')
  => the 2 valid events in this batch (page_view, contact_submission) are lost too
```

`analytics.js:333` only re-queues on `status >= 500 || status === 429`. A 422 falls through, so **every event in that batch is discarded permanently.**

The timing makes this worse than a generic dropped event. `contact_prompt` fires when a visitor clicks a prompt chip; `contact_submission` fires seconds later when they send the message. Both land in the same 2-second / 10-event flush window. **The site's single most valuable analytics event is the one most reliably destroyed by this bug** — which is a strong candidate for why the funnel looks emptier than it should.

**The Fix.** Two independent changes; do both.

```python
# server/schemas/event.py — add the type the client already emits
EventTypeName = Literal[
    "page_view", "click", "scroll_depth", "terminal_command",
    "theme_change", "copy_email", "contact_submission",
    "contact_prompt",           # emitted by form.js:156
    "resume_download", "ai_message_sent", "ai_llm_telemetry",  # see DATA-01
]
```

```js
// frontend/js/analytics.js — never silently drop a batch
if (!response.ok) {
  if (response.status >= 500 || response.status === 429) {
    eventQueue.unshift(...eventsToSend); // transient: retry
  } else if (response.status === 422) {
    console.error(
      "Analytics: batch rejected, dropping",
      eventsToSend.map((e) => e.event_type),
    );
  }
  // 403 => stale session, see BUG-08
}
```

Longer term, make the server partial-accept: validate per event, insert the valid ones, return `{inserted, rejected: [...]}`. A schema drift between two deploys should never cost a whole batch.

## BUG-03 · Concurrent token refresh logs the user out

| Attribute    | Detail                                                                   |
| :----------- | :----------------------------------------------------------------------- |
| **Category** | Bug / Race condition                                                     |
| **Severity** | **High**                                                                 |
| **Location** | `frontend/js/auth.js:279-317`, `server/services/auth_service.py:280-294` |

**The "Why".** `refresh_user_token` rotates: it revokes the presented token and issues a new one. `authenticatedFetch` has no single-flight guard, so when several requests 401 at once — which is exactly what happens when the AI page loads (`/chat/history`, `/auth/me`, `/auth/sessions`) — each fires its own `POST /auth/refresh` with the _same_ refresh token. The first wins. The rest hit:

```python
if not db_token or db_token.is_revoked or ...:
    raise HTTPException(status_code=401, detail="Refresh token has been revoked or expired")
```

and fall through to `clearTokens()` + `auth-changed`. **The user is signed out mid-session for no reason**, and worse, the winning refresh's new token pair is overwritten in `localStorage` by whichever loser writes last.

**The Fix.** Single-flight the refresh:

```js
let refreshInFlight = null;

function refreshOnce() {
  if (refreshInFlight) return refreshInFlight;
  refreshInFlight = (async () => {
    const rt = localStorage.getItem(REFRESH_TOKEN_KEY);
    if (!rt) return null;
    const r = await fetch(`${API_BASE}/auth/refresh`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ refresh_token: rt }),
    });
    if (!r.ok) return null;
    const data = await r.json();
    setTokens(data.access_token, data.refresh_token);
    return data.access_token;
  })().finally(() => {
    refreshInFlight = null;
  });
  return refreshInFlight;
}
```

and have `authenticatedFetch` await `refreshOnce()` instead of refreshing inline. Consider a short server-side grace window (accept a token revoked in the last ~10 s and return the current pair) so a network reorder can't strand a legitimate client.

## BUG-04 · `escapeHTML` does not escape quotes, and is used in attribute position

| Attribute    | Detail                                                                                                       |
| :----------- | :----------------------------------------------------------------------------------------------------------- |
| **Category** | Bug / Security                                                                                               |
| **Severity** | **High**                                                                                                     |
| **Location** | `frontend/js/utils.js:1-5`; used at `chat.js:1345,1388`, `activity.js:528,529`, `activity-charts.js:183,185` |

**The "Why".** `escapeHTML` round-trips through `textContent` → `innerHTML`, which escapes `&`, `<` and `>` but **not `"`**. Six call sites interpolate its output _inside a double-quoted HTML attribute_. Verified:

```
escapeHTML output : hi" onmouseover="alert(1)
rendered attr html: <button data-retry-text="hi" onmouseover="alert(1)">R</button>
parsed attributes  : [ 'data-retry-text', 'onmouseover' ]
onmouseover present: true
```

In `chat.js` the injected value is the user's own message, so it is self-XSS today — but it also plainly _breaks the Retry button_ for anyone whose message contains a quote, which is an ordinary correctness bug.

`activity-charts.js:183/185` is the one to watch. That value is `page_path`, which the client sets to `window.location.pathname + window.location.hash` (`analytics.js:282`) — fully visitor-controlled, **persisted to `user_activity_events`**, and rendered back into `data-path` and `title` attributes. It is session-scoped today, so it stays self-XSS. **It becomes a genuine stored XSS the moment a cross-session admin view exists** — which is precisely what DATA-01 recommends building. Fix this first.

**The Fix.**

```js
export function escapeHTML(value) {
  return String(value)
    .replace(/&/g, "&amp;")
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;")
    .replace(/'/g, "&#39;");
}
```

Better still, stop building attributes by string concatenation: `el.dataset.retryText = text` needs no escaping at all.

## BUG-05 · Chat retry starts a concurrent stream

| Attribute    | Detail                          |
| :----------- | :------------------------------ |
| **Category** | Bug / Race condition            |
| **Severity** | **High**                        |
| **Location** | `frontend/js/chat.js:1413-1422` |

**The "Why".** Every other entry point into `handleChatSubmit` guards on `isGenerating` — the two form handlers (`:1427`, `:1438`), the suggestion cards (`:517`), new chat (`:498`), delete (`:443`), session switch (`:473`). The delegated retry handler does not:

```js
document.addEventListener("click", (e) => {
  const retryBtn = e.target.closest(".retry-btn");
  if (retryBtn) {
    // <- no isGenerating check
    retryBtn.closest(".chat-message")?.remove();
    handleChatSubmit(retryBtn.getAttribute("data-retry-text"));
  }
});
```

A second `handleChatSubmit` overwrites `currentAbortController` (`:1166`), so **the first stream's abort handle is lost** — Stop no longer stops it, and it keeps consuming Bedrock tokens. Both streams then race to `session.messages.push()` and `saveSessions()` (`:1361`), interleaving two replies into one transcript.

Compounding it: the error boundary is appended to _both_ the widget and the AI-page containers, so there are two Retry buttons with the same `data-retry-text` and clicking each fires a separate submit.

**The Fix.** Add the guard, clear the controller when a stream ends, and de-duplicate the buttons:

```js
if (retryBtn) {
  if (isGenerating) return;
  ...
}
// and in handleChatSubmit's finally:
currentAbortController = null;
```

## BUG-06 · Summarisation destroys history before the request that needs it

| Attribute    | Detail                          |
| :----------- | :------------------------------ |
| **Category** | Bug / Data loss                 |
| **Severity** | **High**                        |
| **Location** | `frontend/js/chat.js:1134-1146` |

**The "Why".** Past ~6 000 estimated tokens, the client replaces the entire conversation with a three-message stub and commits it immediately:

```js
session.messages = [
  { text: "Summarize our conversation so far.", sender: "user" },
  { text: sumData.summary, sender: "bot" },
  currentUserMsg,
];
saveSessions(); // <- localStorage overwritten here
restoreActiveSession();
```

The stream that this compaction exists to enable has not been attempted yet. If it then fails — network drop, 500, Bedrock throttle — **the user's long conversation is gone from `localStorage` and unrecoverable**, and all they have is a summary they never asked for.

Secondary effect: the compaction resets the server-side free-message count to two, so `CHAT_FREE_MESSAGE_LIMIT` is bypassed by simply talking long enough.

**The Fix.** Keep the summary out of band until the turn succeeds:

```js
const originalMessages = session.messages.slice();
const outboundMessages = [
  /* the compacted three */
];
// stream with outboundMessages; only on success:
session.messages = [...outboundMessages, { text: botFullText, sender: "bot" }];
saveSessions();
// on failure: session.messages stays === originalMessages
```

## BUG-08 · The persisted event queue is not session-scoped

| Attribute    | Detail                             |
| :----------- | :--------------------------------- |
| **Category** | Bug / Data loss                    |
| **Severity** | Medium                             |
| **Location** | `frontend/js/analytics.js:127-153` |

**The "Why".** The session id lives in `sessionStorage` (per-tab) but the queue lives in `localStorage` under a single shared key `rj_event_queue`, and each queued event carries a baked-in `session_id`. Two failure modes:

1. **Cross-tab.** Tab A writes its queue. Tab B initialises, calls `loadEventQueue()`, and adopts tab A's events — stamped with tab A's session id — then flushes them with tab B's token. `assert_session_access` (`session_token.py:60`) rejects **every event whose id doesn't match the token**, so the batch 403s. 403 is not re-queued, so tab B's own real events in that batch are lost too.
2. **Hard tab kill.** A queue that survives without a `pagehide` is replayed against a brand-new session on next visit, with the same result plus a `console.error("Analytics: Server returned 403")` on essentially every affected load.

**The Fix.** Namespace the key by session and discard on mismatch:

```js
const queueKey = () => `rj_event_queue:${sessionId}`;
function loadEventQueue() {
  if (!sessionId) return;                       // nothing to restore yet
  const stored = localStorage.getItem(queueKey());
  ...
}
```

Call `loadEventQueue()` _after_ the session id is known, and sweep stale `rj_event_queue:*` keys on init.

## BUG-09 · The tuned Bedrock client is never used; three env knobs are dead

| Attribute    | Detail                                                                                                            |
| :----------- | :---------------------------------------------------------------------------------------------------------------- |
| **Category** | Bug / Config                                                                                                      |
| **Severity** | Medium                                                                                                            |
| **Location** | `server/config/bedrock.py:11-21`, `server/services/bedrock_service.py:116-121`, `server/config/settings.py:63-65` |

**The "Why".** `config/bedrock.py` builds a correctly configured runtime client — `connect_timeout=10`, `read_timeout=BEDROCK_TIMEOUT_SECONDS`, `retries={"max_attempts": 2}`. A repo-wide grep finds exactly one reference to it:

```
server/config/bedrock.py:18:bedrock_runtime = boto3.client(
```

Nothing imports it. `BedrockService` builds its own instead, with no `Config` at all:

```python
self._client = boto3.client("bedrock-runtime", region_name=self.region_name)
```

So the chat path runs on botocore defaults (60 s read timeout, default retry mode). A hung Bedrock connection occupies one of the four `CHAT_MAX_CONCURRENCY` slots for a minute instead of thirty seconds.

Three settings are validated at import, documented in the README, and read by no code path they name:

| Setting                             | Named for            | Actually used by                                   |
| :---------------------------------- | :------------------- | :------------------------------------------------- |
| `BEDROCK_TIMEOUT_SECONDS`           | Bedrock read timeout | only the unused `bedrock_runtime`                  |
| `CHAT_STREAM_QUEUE_SIZE`            | streaming queue size | nothing — `bedrock_service.py:21` hardcodes `64`   |
| `BEDROCK_QUEUE_PUT_TIMEOUT_SECONDS` | queue put timeout    | nothing — `bedrock_service.py:17` hardcodes `10.0` |

**The Fix.** Import the shared client and wire the constants:

```python
# bedrock_service.py
from server.config.bedrock import bedrock_runtime
from server.config.settings import CHAT_STREAM_QUEUE_SIZE, BEDROCK_QUEUE_PUT_TIMEOUT_SECONDS

_QUEUE_PUT_TIMEOUT_SECONDS = BEDROCK_QUEUE_PUT_TIMEOUT_SECONDS
_STREAM_QUEUE_SIZE = CHAT_STREAM_QUEUE_SIZE

@property
def client(self):
    return bedrock_runtime
```

Add a test asserting the chat client's `_client_config.read_timeout` matches the setting, so this cannot silently drift again.

## BUG-10 · Seven auth error paths render `[object Object]`

| Attribute    | Detail                                        |
| :----------- | :-------------------------------------------- |
| **Category** | Bug / UX                                      |
| **Severity** | Medium                                        |
| **Location** | `frontend/js/auth.js:64,75,87,99,213,233,253` |

**The "Why".** `getErrorMessage()` exists specifically to flatten FastAPI's `detail`, which is a _list of objects_ for any 422. Seven functions bypass it:

```js
throw new Error(err.detail || "Failed to setup 2FA");
```

When `detail` is `[{loc:…, msg:…}, …]`, `new Error(array)` stringifies to `"[object Object],[object Object]"` — and `auth-ui.js` writes `err.message` straight into the visible error element. Password-policy rejections on reset, change-password and delete-account are exactly the 422s users hit most.

**The Fix.** Replace all seven with `getErrorMessage(err, '…')`. It already handles the array case.

## BUG-12 · Swipe navigation: stale origin, wrong breakpoint, no re-init

| Attribute    | Detail                                                                    |
| :----------- | :------------------------------------------------------------------------ |
| **Category** | Bug                                                                       |
| **Severity** | Medium                                                                    |
| **Location** | `frontend/js/swipe-handler.js:34-77`, `frontend/js/navigation.js:229-231` |

Three distinct problems:

1. **Stale gesture origin.** `handleTouchStart` returns early when the touch begins on an interactive element, leaving `startX/startY/startTime` at their previous values. `handleTouchEnd` filters independently on _its own_ target, which can differ (start on a button, release on the background). The delta is then measured from a stale origin. There is no "gesture armed" flag tying the two together.
2. **Wrong breakpoint.** `initSwipeGestures()` is gated on `compactViewport` (`max-width: 1150px`), so horizontal swipes navigate sections on 1024 px laptops and iPads with trackpads. `mobileDevice` (`pointer: coarse and max-width: 768px`) is the query that means "phone", and `chat.js` already uses 768.
3. **No re-init on resize.** The check runs once at load. Rotate a tablet from 1200 px landscape to 800 px portrait and swipe never activates; go the other way and it never deactivates.

`.no-swipe` covers the terminal and skills carousel, but 9 other `overflow-x: auto` regions (activity tables, chat code blocks) are not excluded — swiping to scroll one jumps sections.

**The Fix.**

```js
handleTouchStart(e) {
  this.armed = !e.target.closest('input, textarea, select, button, a, .no-swipe, [data-scroll-x]');
  if (!this.armed) return;
  ...
}
handleTouchEnd(e) {
  if (!this.armed) return;
  this.armed = false;
  ...
}
```

Gate on `mobileDevice`, keep the handler reference, and re-evaluate on `mobileDevice.addEventListener('change', …)` calling `destroy()` / re-construct.

## BUG-13 · The global rejection handler suppresses every console error

| Attribute    | Detail                     |
| :----------- | :------------------------- |
| **Category** | Bug / Observability        |
| **Severity** | Medium                     |
| **Location** | `frontend/js/main.js:2-14` |

**The "Why".** `event.preventDefault()` runs unconditionally on every unhandled rejection. That is the call that tells the browser "handled — don't report this", so **no unhandled rejection ever appears in the console** and none reaches `window.onerror`. Combined with DATA-02 (nothing is reported to the server either), production JS failures are invisible to everyone.

**The Fix.** Report first, suppress only what you have actually handled:

```js
window.addEventListener("unhandledrejection", (event) => {
  console.error("Unhandled promise rejection:", event.reason);
  reportError(event.reason); // see DATA-02
  const msg = String(event.reason?.message || "");
  if (/fetch|network/i.test(msg)) {
    showToast("Network error. Please check your connection.", "error");
    event.preventDefault(); // this one is genuinely handled
  }
});
```

Note the same module is why `frontend/js/error-handler.js` — 139 lines of `AppError`/`NetworkError`/`APIError` classes — is orphaned (LOW-01). Wire it up or delete it.

Four issues in one flow:

**Location:** `frontend/js/analytics.js:86-92`, `server/auth/session_token.py:68-80`

## SEC-04 · `/chat` is not on the strict rate-limit budget; SSE streams are uncapped

# 2. Performance

## 2.1 PERF-01 · Three CDN origins in the critical rendering path — **[measured]**

This is the finding with the largest real-world impact, and the numbers are unambiguous.

Two headless Chromium loads of the same page, same machine, same server:

| Scenario                                                 | First Paint |           FCP | DOMContentLoaded |
| :------------------------------------------------------- | ----------: | ------------: | ---------------: |
| CDNs unreachable, requests hang until the proxy gives up |   12 664 ms | **13 176 ms** |        14 547 ms |
| Cross-origin requests fail instantly (site's own cost)   |       84 ms |    **448 ms** |           734 ms |

**The site's own assets are fast.** The entire ~12.7-second delta is third-party. Three separate origins can each independently stall first paint or app init:

| Resource                         | Origin               | Why it blocks                                                                                                                                                   |
| :------------------------------- | :------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `all.min.css` (Font Awesome)     | cdnjs.cloudflare.com | `<link rel="stylesheet">` — render-blocking, no `media` trick                                                                                                   |
| `css2?family=Plus+Jakarta+Sans`  | fonts.googleapis.com | render-blocking stylesheet                                                                                                                                      |
| `purify.min.js`, `marked.min.js` | cdn.jsdelivr.net     | `index.html:1655,1658` — **classic scripts with no `defer` or `async`**, so they block `DOMContentLoaded`, and `main.js` does all of its init inside that event |

The third row is the sharpest: `chat.js` is carefully lazy-loaded on first interaction, but its two dependencies (~60 KB) are fetched eagerly and synchronously on every single page load — including for the majority of visitors who never open the chat. And because they gate `DOMContentLoaded`, a jsdelivr hiccup delays theme application, navigation, analytics and everything else.

This is not hypothetical: corporate proxies, ad blockers and regional blocking all produce exactly the hang measured above.

**The Fix**, in order of value:

1. **`defer` the two jsdelivr scripts today** (one-word change, removes them from the `DOMContentLoaded` critical path).
2. **Better: move them into `chat.js`.** Load them dynamically the first time `renderBotHTML` needs them. `renderBotHTML` already degrades safely when they are absent (`chat.js:15-26`), so the fallback path is proven.
3. **Self-host the fonts and icons.** They are already in the service-worker allowlist, i.e. already treated as app-shell. Serving them from the same origin removes two DNS+TLS handshakes _and_ two single points of failure. Font Awesome's two preloaded `woff2` files are ~255 KB for perhaps 40 glyphs — subset them, or inline the icons as SVG sprites and drop the dependency entirely.
4. Add `media="print" onload="this.media='all'"` to the Font Awesome stylesheet as an interim so it cannot block paint.

## 2.5 PERF-05 · The service worker undoes the lazy-loading

`main.js` goes to real trouble to defer `chat.js`, `activity.js` and `three-bg.js` behind interaction and `requestIdleCallback`. `sw.js:13-53` then precaches **all 40 of them** on install, including `/js/chat.js` (51 KB), `/js/activity.js` (37 KB) and `/three-bg.js` (49 KB). Every first-time visitor downloads the entire app regardless.

Three further problems in the same file:

- **`cache.addAll` is all-or-nothing.** One 404 in that 40-entry list — a renamed module, a deploy race — and the service worker never installs at all. There is no per-URL tolerance.
- **Stale-while-revalidate on `/` and `/index.html`** directly contradicts `.htaccess`'s `no-cache, no-store` for HTML, and means a returning visitor gets the _previous_ deploy's HTML paired with the _current_ deploy's JS. With no content hashing (CICD-02) and an in-place `rsync`, this version skew is likely, not theoretical.
- **`skipWaiting()` inside `install`** means the new worker activates and claims clients immediately, so the "A new version is available!" banner in `main.js:239` fires _after_ the swap has already happened.

**The Fix.** Precache only the true app shell (`/`, `styles.css`, `main.js`, `config.js`, `navigation.js`, `theme.js`, `utils.js`, the profile image) and let everything else populate on demand. Use `Promise.allSettled` over individual `cache.add` calls. Serve HTML network-first. Move `skipWaiting()` behind a `postMessage` from the banner's Refresh button so the user chooses the moment.

`event_controller.py:239-243` emits both a named `activity` frame _and_ an unnamed back-compat frame for the same event:

## A11Y-01 · The auth modal is not a managed dialog — [browser-verified]

| Attribute    | Detail                                                      |
| :----------- | :---------------------------------------------------------- |
| **Severity** | **High**                                                    |
| **Location** | `frontend/js/auth-ui.js:76-127`, `frontend/index.html:1258` |

The project has a good modal implementation in `modal.js` — focus trap, reference-counted scroll lock, focus restore, Escape. The auth modal uses none of it; it just toggles a class. Measured:

```
auth modal opened:  {"open":true, "focus":"nav-login-btn", "scrollLocked":false}
after Escape     :  {"open":true}
```

So: focus never enters the dialog, Tab walks straight out into the page behind it, the background scrolls, and **Escape does not close it** — despite `role="dialog" aria-modal="true"` promising all of that.

Four more issues in the same component:

- `ModalSwipeDismiss` sets `aria-hidden="true"` on close (`auth-ui.js:9-12`), but the eight `modal.classList.remove('hidden')` call sites never clear it. **After one swipe-dismiss, every subsequent open is invisible to screen readers.**
- `aria-labelledby="auth-modal-title"` points at an `<h3>` inside the _login_ panel. On the register, 2FA, magic-link, sessions, change-password and delete-account tabs that element is hidden, so the dialog has no accessible name.
- `.auth-tab` buttons have no `role="tab"`, `aria-selected` or `aria-controls`.
- `<div class="auth-error" id="login-error">` has no `role="alert"` or `aria-live`, so login failures are never announced.

**The Fix.** Route it through `modal.js`:

```js
import { openModal, closeModal } from "./modal.js";

window.addEventListener("request-login-modal", () => {
  modal.classList.remove("hidden");
  modal.removeAttribute("aria-hidden");
  switchTab("login");
  openModal(modal, { initialFocus: document.getElementById("login-email") });
});
```

Give each tab panel its own `<h3 id>` and point `aria-labelledby` at the active one in `switchTab`. Add `role="alert"` to the six `.auth-error` divs.

## A11Y-03 · Dropdown panels lack keyboard semantics

**Location:** `frontend/index.html:254-390`, `frontend/js/navigation.js:157-176`

What is right: `aria-expanded` and `aria-controls` on the toggles, `aria-hidden` maintained on the panels, Escape closes and returns focus, and `visibility: hidden` correctly removes closed panels from the tab order.

## Theme consistency

**Dark preference is ignored on first visit — [browser-verified].** With `prefers-color-scheme: dark` and nothing in `localStorage`:

```
{"darkClass": false, "bodyBg": "rgb(248, 250, 251)", "themeColorMeta": "hsl(38, 92%, 50%)"}
```

Both the inline bootstrap (`index.html:130-136`) and `initTheme()` (`theme.js:54`) key only off a saved value. `prefersDarkScheme` is watched (`theme.js:59`) but only fires when the OS setting _changes_ mid-session. So a dark-mode user gets a white flash and a light site, on a site whose own `manifest.json` declares `"background_color": "#0a0e14"`.

```js
// index.html inline bootstrap
var saved = localStorage.getItem("theme");
var dark = saved
  ? saved === "dark"
  : window.matchMedia("(prefers-color-scheme: dark)").matches;
if (dark) document.body.classList.add("dark-theme");
```

and mirror it in `theme.js`: `applyTheme(saved ? saved === "dark" : prefersDarkScheme.matches)`.

**Customizer / bootstrap disagree about `--text`.** `theme-bootstrap.js:8-16` applies _every_ key in the saved palette. `applyPaletteVariables` (`theme-customizer.js:75-85`) explicitly removes and skips `--text`. Current palettes (`version: 1`) don't emit `--text`, so this only bites users carrying a pre-v1 palette — for whom the body text colour visibly flips at `DOMContentLoaded`. The bootstrap has no `version` check. Add one.

**Contrast is not validated.** `getContrast()` exists (`theme-customizer.js:44`) but is used only to choose black-or-white foreground for the accent fill (`:56-57`). `--accent-text` and `--data-text` — used for links and headings against `--bg` — are never checked. The panel's own copy promises _"We'll automatically generate accessible light and dark variants."_ It generates variants; it does not verify them. Gate Apply on a ≥4.5:1 check, or clamp lightness until it passes.

## DATA-01 · Everything is session-scoped

Every read endpoint takes a `session_id` and requires that session's capability token:

```
GET /sessions/{id}/events           GET /sessions/{id}/events/summary
GET /sessions/{id}/events/funnel    GET /sessions/{id}/stream
```

There is no endpoint that answers _"how many people visited this week"_, _"which section holds attention"_, or _"how many résumé downloads did that post drive"_. The `#activity` dashboard shows a visitor **their own** trail — a nice demo, but it is not analytics for the site owner. The data is being collected diligently and read by nobody.

Three structural gaps behind that:

1. **No owner role.** `users` has no `role`/`is_admin` column and `role_utils.py` is about Bedrock message roles, not authorisation.
2. **Sessions are never linked to users.** Migration `c2d3e4f5a6b7` added `user_sessions.user_id`, but `create_session` (`session_controller.py:30`) never sets it. Logged-in behaviour cannot be distinguished from anonymous.
3. **No rollups.** Every query scans `user_activity_events` by `session_id`. There is no daily aggregate, so a site-wide query would scan the whole table.

# 6. CI/CD and rollback

## What exists, and it is better than most

`.github/workflows/deploy.yml` is a genuinely careful pipeline, and the reasoning is written into the comments:

- Four gates before deploy: frontend lint + tests, backend ruff + pytest on 3.10 and 3.12 with `--cov-fail-under=55`, and a **migration job** that runs the full chain against real PostgreSQL 16, asserts a single head, runs `alembic check` for model/migration drift, and verifies reversibility with `downgrade base && upgrade head`.
- Hash-checked dependency installs (`pip install --require-hashes`) in both CI and on the host.
- `ref: ${{ github.sha }}` — deploys the commit that was tested, not whatever `main` points at now.
- `concurrency: production-deploy` with `cancel-in-progress: false`, so two merges queue rather than interleave two `rsync --delete` passes and two migrations.
- A pre-deploy source sanity check that refuses to mirror a near-empty directory over the live web root.
- A **snapshot before every deploy** (`server.prev`, `html.prev`, `alembic-revision.prev`) and an automatic rollback on failure, followed by a rollback _verification_ step.
- A real health gate — `systemctl is-active` plus 12 polls of `/api/health` requiring `"status":"ok"` — with the comment correctly noting that a successful `systemctl restart` does not mean the app came up.

That is a solid foundation. The gaps below are about depth and confidence, not basic hygiene.

## CICD-01 · No staging environment (High · L)

`deploy` runs only on `push` to `main`. There is no pre-production target, so **the first machine to run a merged commit is production**. `analytics.js:13` already routes any hostname containing `staging` to `https://staging-api.rjasti.com/api` — the frontend expects a staging tier the pipeline never builds.

Consequence: the health check is the only runtime verification, and it only proves FastAPI can reach PostgreSQL. A deploy that breaks Bedrock credentials, the CORS origin list, the Apache `/api` prefix, or the service worker passes green while Ask AI is down.

## CICD-02 · No build step (High · M)

`npm run` offers lint, format, test and audit. `rsync` copies `frontend/` verbatim. Therefore:

- No minification — `styles.css` ships 211 KB of source with comments and region markers.
- No bundling — 37 requests on first load.
- No tree-shaking — hence the 1.3 MB dead `three.module.js` (PERF-03) reaching the web root.
- **No content hashing** — which is what forces `.htaccess` into `max-age=3600, must-revalidate` for all CSS and JS, and what makes the service-worker version skew in PERF-05 possible.

## CICD-03 · Coverage gaps in the gates (Medium · S)

- `lint:js` globs `frontend/js/*.js` and `frontend/js/terminal/*.js`. It **misses `frontend/three-bg.js` (1 515 lines) and `frontend/sw.js` (185 lines)** — the two most consequential unlinted files, one of which controls caching for every returning visitor.
- `npm run audit` exists and is **never called by the workflow**. It currently reports **8 high-severity advisories** (postcss path traversal, `ws` memory disclosure and DoS, via stylelint and jsdom). Dev-only today, but nothing enforces that.
- No CodeQL, no dependency review, no secret scanning.
- `npm run format:check` is defined and never run. **57 of the repo's files are not Prettier-clean**, so the formatter exists as a suggestion rather than a gate — which is why formatting noise will show up in every future diff.
- Frontend tests cover 5 of ~30 modules (`activity-charts`, `app-logic`, `contact-form`, `terminal`, `utils`). Nothing tests `analytics.js`, `chat.js`, `auth.js` or `sw.js` — the four modules holding most of the bugs in §1.

## CICD-04 · Rollback depth is one release (High · S)

`Snapshot Current Release for Rollback` overwrites the same two directories every run:

```bash
rsync -a --delete "$APP_DIR/server/" "$BACKUP_DIR/server.prev/"
sudo rsync -a --delete "$WEB_ROOT/"  "$BACKUP_DIR/html.prev/"
```

So `server.prev` always holds exactly one release. **Two bad deploys in a row and the good release is gone** — the second snapshot captures the first bad deploy. Recovery then means a manual redeploy from a git ref.

Related: the frontend deploy is an in-place `rsync --delete` into Apache's live document root. There is a window, however brief, during which the site is serving a mix of old and new files — precisely the version skew PERF-05 describes.

## CICD-05 · The health check is not a smoke test (Medium · S)

`/api/health` runs `SELECT 1`. It does not exercise Bedrock, session creation, event ingestion, or whether Apache is stripping the `/api` prefix as the dual-mount in `main.py:106-118` hedges against. Those are the four things most likely to break in a deploy.

## Rollback runbook

### Target architecture

Move from in-place mirroring to **versioned releases with an atomic symlink switch**. This is the change that makes everything else in this section straightforward.

```
/home/<user>/fastapi/
├── releases/
│   ├── 2026-09-01T10-14-22_ec37e95/     # each is a complete, immutable release
│   ├── 2026-08-30T09-02-11_b2431d1/
│   └── …                                 # keep the last 10
├── current -> releases/2026-09-01T10-14-22_ec37e95   # atomic switch point
└── shared/
    ├── .env
    └── deploy-backups/
```

`/var/www/html` becomes a symlink to `current/frontend` (Apache needs `FollowSymLinks`, already implied by `.htaccess` working).

Deploy becomes: rsync into a **new** release directory → install deps → migrate → `ln -sfn` + `mv -T` the symlink (atomic) → reload. Rollback becomes: repoint the symlink and reload. Sub-second, and depth is however many releases you keep.

### Step 0 — Preconditions

```bash
ssh "$EC2_USER@$EC2_HOST"
ls -1t ~/fastapi/releases | head -10        # what can I roll back to?
readlink ~/fastapi/current                  # what is live now?
cat ~/fastapi/shared/deploy-backups/alembic-revision.prev
curl -fsS https://rjasti.com/api/health
```

### Step 1 — Decide: is this a code problem or a schema problem?

```bash
cd ~/fastapi/current/server
~/fastapi/.venv/bin/alembic current                    # live schema revision
~/fastapi/.venv/bin/alembic history -r current:head    # anything applied since?
```

- **No migration in the bad deploy** → Step 2, done in seconds.
- **A migration ran** → Step 2 still applies, **but read Step 4 first.** The workflow deliberately never runs `alembic downgrade`, and that is the right call.

### Step 2 — Roll back the code (target: < 60 s)

```bash
PREV=$(ls -1t ~/fastapi/releases | sed -n 2p)          # or a named release
ln -sfn ~/fastapi/releases/$PREV ~/fastapi/current.new
mv -Tf ~/fastapi/current.new ~/fastapi/current         # atomic: no partial state
sudo systemctl restart fastapi.service
sudo systemctl reload httpd                            # reload, not restart
```

Until the release layout lands, the equivalent using today's snapshots — this is what the workflow's failure path already does, and it is safe to run by hand:

```bash
APP_DIR=~/fastapi; BACKUP_DIR="$APP_DIR/../deploy-backups"
rsync -a --delete "$BACKUP_DIR/server.prev/" "$APP_DIR/server/"
sudo rsync -a --delete "$BACKUP_DIR/html.prev/" /var/www/html/
"$APP_DIR/.venv/bin/pip" install --require-hashes -r "$APP_DIR/server/requirements.txt"
sudo systemctl restart fastapi.service && sudo systemctl restart httpd
```

### Step 3 — Verify (do not skip)

```bash
for u in fastapi.service httpd; do systemctl is-active --quiet $u || echo "DOWN: $u"; done
curl -fsS https://rjasti.com/api/health | grep -q '"status"[[:space:]]*:[[:space:]]*"ok"' \
  && echo "health OK" || echo "HEALTH FAILED"

# Smoke test — the four things /health does not cover:
SID=$(curl -fsS -X POST https://rjasti.com/api/sessions \
        -H 'Content-Type: application/json' -d '{"device_type":"desktop"}')
echo "$SID" | grep -q session_token && echo "sessions OK"
curl -fsS -o /dev/null -w '%{http_code}\n' https://rjasti.com/           # 200
curl -fsS -o /dev/null -w '%{http_code}\n' https://rjasti.com/api/health # 200, proves prefix routing
```

Then confirm in a browser: theme toggle, one Ask AI message, one contact submit.

### Step 4 — Database: expand / contract, never downgrade

The workflow's comment is correct and worth restating as policy:

> The database is deliberately NOT downgraded: `alembic downgrade` can drop columns and lose rows, so migrations must stay backward-compatible with the release before them.

**The rule: every migration must leave the schema readable by release N−1.**

| Change          | Safe now                                     | Deferred to a later deploy |
| :-------------- | :------------------------------------------- | :------------------------- |
| Add a column    | `nullable=True` **or** with `server_default` | make `NOT NULL`            |
| Rename a column | add new, dual-write both                     | drop old                   |
| Drop a column   | stop writing it                              | drop it                    |
| Change a type   | add new column, backfill, dual-write         | drop old                   |
| Add an index    | `CREATE INDEX CONCURRENTLY`                  | —                          |

If a deploy has already applied a destructive migration and you must go back, restore from the RDS/PostgreSQL snapshot taken immediately pre-deploy (Step 5 adds it) and replay whatever writes occurred in the window. Treat that as an incident, not a rollback.

### Step 5 — Pipeline changes that make this routine

Ordered by value per hour of work:

1. **Versioned releases + atomic symlink** (M) — everything above; turns rollback into one command and eliminates the mixed-content window.
2. **Keep the last 10 releases** (S) — fixes CICD-04's depth-1 problem outright.
3. **Pre-migration database snapshot** (S) — before `alembic upgrade head`, take an RDS snapshot or `pg_dump` tagged with the commit SHA. Currently only the _revision string_ is recorded, which tells you where you were but does not get you back there.
4. **Promote the health gate to a smoke test** (S) — add the Step 3 checks to the workflow so a Bedrock or routing failure trips the automatic rollback that already exists.
5. **A staging environment** (L) — CICD-01. A `staging` branch deploying to a second EC2 target and `staging.rjasti.com`, running the same smoke suite. The frontend already routes to it.
6. **A build step** (M) — CICD-02. `npm run build` producing minified, content-hashed assets into `dist/`, deploy `dist/` instead of `frontend/`. Then flip `.htaccess` CSS/JS to `max-age=31536000, immutable`, and generate `sw.js`'s precache list from the manifest so it can never 404 mid-`addAll`.
7. **Feature flags** (M) — a `flags` table plus `GET /api/flags` (cached, ~60 s), with the client reading them at boot. Ship `ask_ai_enabled`, `activity_dashboard_enabled`, `chat_model_id`. This gives a **sub-second kill switch for Ask AI**, which matters directly for SEC-01: today, disabling chat under a cost incident requires a code deploy.
8. **Close the CI gaps** (S) — extend `lint:js` to `frontend/*.js`; add `npm run audit` as a job; add CodeQL and dependency review.
9. **Blue-green** (L) — only worth it after (1) and (5). Two systemd units on different ports with nginx/Apache switching upstream: zero-downtime deploys and instant reversal. A single EC2 host makes canary-by-traffic-percentage awkward; if you want progressive delivery, do it with feature flags (7), which is cheaper and fits the architecture.
