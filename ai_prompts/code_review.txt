# Whole-Codebase Audit Prompts

All read-only. `/review` and `/security-review` scope themselves to a **diff** —
they are the per-PR tools. What follows is the whole-repo pass.

Run each in a fresh session (`/clear` between). Topics bleed into each other
otherwise, and each audit reads a different slice of the repo — mixing them is
what blows the navigation budget. These are read-only, so a Claude Code web
session per topic works well: each writes its own `docs/review/*.md` on its own
branch.

Paste **§A** above whichever prompt you run. Without it an auditor re-reports
closed findings, proposes a framework, and reads `styles.css` end-to-end.

---

## A. Shared preamble — paste above every prompt below

```
Read-only. No edits, no commits, no PR.

Binding context:
- `AGENTS.md` "Non-Goals" are standing decisions.
  Arguing against one is allowed; doing it silently
  is not.
- `.claude/REVIEW.md` §1 defines four automatic
  Criticals: a frontend framework or JSX (ADR-001),
  a third-party asset origin in the SPA (ADR-016),
  a client-sent model ID, system prompt or token
  ceiling (ADR-023), and any endpoint outside the
  three guard tiers that `docs/SECURITY.md` does not
  list as anonymous.
- `POST /chat` and `POST /sessions` are deliberately
  anonymous. Not a finding.
- `ucl.html` and `worldcup.html` load Google Fonts,
  cdnjs and FlagCDN on purpose. Not a finding, and
  not precedent for the SPA.
- Read the status header of every `docs/review/*.md`
  before you start. Do not re-report a closed
  finding. If you believe one regressed, say so and
  cite the line as it stands now.

Budget:
- `.claude/rules/navigation.md` is binding. Never
  read `frontend/styles.css`, `frontend/index.html`,
  `js/chat.js`, `js/auth-ui.js` or
  `package-lock.json` end-to-end. Grep the region or
  function map, then `sed -n` the range.
- Same for `docs/**` per
  `.claude/rules/reference-docs.md`: heading map
  first, then the one section.
- Bash searches under `server/` need
  `--exclude-dir=.venv`.

Traps that produce a false clean bill:
- An auth-coverage grep on `@router` misses
  `session_routes.py`, `system_routes.py` and
  `event_routes.py` — they register through
  `router.add_api_route(...)`.
- A fresh clone has no `node_modules` and no backend
  packages. Install before you judge a failure.

Output: the finding table in `AGENTS.md` §5 —
Category | Severity | `file:line` | the Why | the Fix.
Every entry names the input or path that produces the
wrong result. Mark a guess as a guess. Zero filler,
no "you could also".
```

## C. The prompts

**1. Correctness**
```
Read-only pass. Find correctness bugs.

Look for: swallowed exceptions, race
conditions, boundary/off-by-one cases,
null paths, non-idempotent retries,
transaction scope too wide or narrow,
silent type coercion.

Write docs/review/bugs.md:
severity P0-P3 | file:line | what breaks
and on what input | the fix.

Open with a Scope table: what you read and
what you did not. Skip style. Only report
things with a concrete failure mode.
```

**2. Security** *(never run — no `docs/review/security.md` yet)*
```
Read-only security review of the repo.
Follow the `security-audit` skill's
checklist, then go past it.

Cover: authz gaps on non-obvious paths —
every route in server/controllers/ mapped
to its guard tier; injection (SQL, shell,
template, email header); secrets in code,
config or CI; unsafe deserialization;
SSRF on the outbound calls (HIBP,
Bedrock, FormSubmit); validation at trust
boundaries; refresh-token rotation and
lockout logic; the trusted-proxy and CORS
settings; the three pinned CSP hashes;
dependency CVEs from package-lock.json
and the hash-pinned requirements files.

Write docs/review/security.md:
severity | file:line | attack path | fix.

Split "exploitable today" from
"hardening". Reconcile against the ten
rows in docs/SECURITY.md "Known
limitations" — say which are still true,
which are now wrong, and what is missing
from that table.
```
Then pair `/security-review` with every diff that touches auth, tokens, rate
limits, the CSP or user-controlled output.

**3. Performance** *(never run — no `docs/review/performance.md` yet)*
```
Read-only performance review.

Backend: N+1 queries, queries with no
index support, SELECT * on wide tables,
missing pagination, blocking I/O on async
paths, per-request work that could be
cached or batched, unbounded memory growth
(the in-memory rate limiter and the
ingest buffer especially), I/O in hot
loops, SSE stream lifetime and the Kafka
batch flusher / PG fan-out tasks.

Frontend: first paint and the module
graph, the 2.3 MB of shelf PNGs, service
worker cache strategy, layout thrash,
listener and observer leaks, work on
scroll or resize without rAF, the cost of
a 13,648-line stylesheet.

Per finding: the code path, why it is
slow, rough magnitude, the fix.
Write docs/review/performance.md.

Say which ones need a profile or an
EXPLAIN to confirm instead of asserting
them. Check findings against the CI size
budget added by anti-slop.md finding 5.
```

**4. UI/UX**
```
Read-only review of the UI layer.

Cover: missing loading/empty/error states,
inconsistent components doing the same job,
forms with no validation feedback, focus
order and keyboard traps, contrast, touch
targets, destructive actions with no
confirm, flows that leave the visitor
unsure whether something worked.

Use the `accessibility` skill for the
WCAG 2.2 AA calls.

Write docs/review/uiux.md with file:line
and the concrete change. Rank by traffic
on the affected path, not by severity
alone — tier 1 is every visitor on every
section.
```

**5. Features**
```
Read @README.md and the codebase, then
propose features.

Context — audience in priority order:
(1) visitors and recruiters, for whom the
SPA is the product and first paint,
mobile layout and accessibility outrank
internal elegance; (2) the code itself as
a work sample, so "a framework would be
less code" is not an argument; (3) the
owner, whose Activity dashboard and AI
chat are personal tools and demos, not a
product with external users. Standing
roadmap: ADR-011 and ADR-012 (both
Proposed) plus the open rows in
docs/SECURITY.md "Known limitations".
No complaint stream exists — infer the
user problem from code behaviour and say
that you did.

Per idea: the user problem, why this
codebase is positioned for it, rough
implementation shape, effort (S = a
sitting, M = a weekend, L = more).
Rank by value-to-effort, not value.

Flag anything already half-built. No
generic "portfolios should have X" — every
proposal points at code that exists today:
a half-built surface, a duplicated fact,
or an unread table.
```
Then run the SDLC loop in `sdlc.txt` per accepted idea — `intent-planner` writes
`.claude/intents/YYYY-MM-DD-<slug>.md`, then the companion spec, then build.

**6. Per-surface deep dive** *(what produced `apps-uiux.md`)*
```
Read-only UI/UX and feature review of
<surface>, and nothing else.

State up front which prior review covered
the neighbouring surfaces and why this one
was missed.

Before proposing anything, read
.claude/intents/ for decisions already
made about this surface. Open with a
"Standing decisions this review does not
reopen" table: decision | where it is
recorded. If a finding does cross one, say
so explicitly and argue it — do not
smuggle it in.

Then a Verdict paragraph: what is in good
shape, and where the gaps concentrate.
Then findings, grouped per sub-surface.

Write docs/review/<surface>.md.
```

**7. Design-system consistency** *(what produced `anti-slop.md`)*
```
Read-only audit of the design system's
enforcement, not its taste.

For each visual dimension — colour,
spacing, type, motion, elevation — answer:
is there a scale, is it in docs/DESIGN.md,
and is it actually adopted in
frontend/styles.css? Give the adoption
count and the command you measured it
with.

Then: is any scale duplicated between CSS
and JS? Is the rationale reachable from
the docs? Does CI gate weight or size at
all?

Verify every count twice — a multi-line
`transition` declaration defeats a
line-based `grep -c`, and a
`cubic-bezier()` in the token block is a
definition, not a duplicate. If a
measurement was wrong on first pass,
correct it in the document rather than
restating it silently.

Write docs/review/anti-slop.md, with a
summary table: # | finding | severity.
```

**8. Instruction-file audit**
```
Audit .claude/CLAUDE.md, AGENTS.md,
.claude/skills/, and .claude/agents/
against the actual code.

Flag: rules the codebase contradicts,
rules restating what's derivable from the
repo, conflicts between files, and rules
that should be path-scoped or a hook.

Report only — don't rewrite.
```

**9. Agentic setup**
```
Audit my agentic setup for this repo:
.claude/CLAUDE.md, .claude/skills/, .claude/agents/,
.claude/hooks/, and .claude/settings.json.

Tell me:
1. Advisory rules that should be enforced
   — propose the PreToolUse hook for each
2. Rules that should be path-scoped
   rather than always loaded
3. What's missing: test gate, formatter,
   guard on destructive commands
4. Permissions too broad, and prompts I
   could safely allowlist
5. Subagents whose tool lists are wider
   than their job

Table first, then the files you'd write.
Don't write them yet. Respect docs/ECC.md:
a fourth vendored ECC skill or a foreign
hook fails check_agent_config.py.
```
`context-budget` is the skill for the token half of this.

**10. Triage**
```
Read docs/review/*.md, including the
status header of each. Produce one
prioritized fix list over everything still
open, deduped, P0 first.

Per item: the fix, blast radius, whether
it needs a test, and which gate proves it
(check_docs.py, check_csp_hashes.py,
pytest, npm test, npm run lint).

Group into batches that ship independently
and name the batch a single PR should
carry. Don't fix anything.
```

## D. Fan-out

Three read-only specialists exist and are denied `Write`/`Edit` in their
frontmatter, so they cannot drift into fixing things:

| Agent | Use for |
| :--- | :--- |
| `.claude/agents/backend-reviewer.md` | FastAPI routes, async correctness, ORM patterns, rate limits, Pydantic schemas |
| `.claude/agents/frontend-reviewer.md` | ES modules, CSP compliance, DOM sanitization, CSS tokens, frontend performance |
| `.claude/agents/security-reviewer.md` | auth, endpoints, secrets, CSP, egress policy |

Delegate explicitly when a topic spans tiers — "run prompt 3 against `server/`
via `backend-reviewer` and against `frontend/` via `frontend-reviewer`, then
consolidate" — rather than letting one context carry both halves.

## E. After the audit

1. Triage with prompt 10 into batches, one PR each.
2. Per accepted feature, the `sdlc.txt` loop: intent doc, then spec, then build.
3. Implement on a branch per batch. `/verify` before pushing; the gates are
   `PYTHONPATH=. pytest`, `npm test`, `npm run lint`, `python3
   scripts/check_docs.py --fix`, `python3 scripts/check_csp_hashes.py`.
4. Update the finished review doc's status header with what shipped, what was
   wrong in the review itself, and what stayed open. Then update §B above.
