All read-only. Run each in a fresh session (`/clear` between) so findings don't bleed together.

**1. Correctness**
```
Read-only pass. Find correctness bugs.

Look for: swallowed exceptions, race
conditions, boundary/off-by-one cases,
null paths, non-idempotent retries,
transaction scope too wide or narrow,
silent type coercion.

Write docs/review/bugs.md:
severity P0-P3 | file:line | what breaks
and on what input | the fix.

No edits. Skip style. Only report things
with a concrete failure mode. Mark
guesses as guesses.
```

**2. Security**
```
Read-only security review of the repo.

Cover: authz gaps on non-obvious paths,
injection (SQL, shell, template), secrets
in code/config/CI, over-broad IAM and DB
grants, unsafe deserialization, SSRF,
validation at trust boundaries, dependency
CVEs from the lockfiles.

Write docs/review/security.md:
severity | file:line | attack path | fix.

Split "exploitable today" from "hardening."
```
Pair with `/security-review` on each diff going forward.

**3. Performance**
```
Read-only performance review.

Cover: N+1 queries, queries with no index
support, SELECT * on wide tables, missing
pagination, blocking I/O on async paths,
per-request work that could be cached or
batched, unbounded memory growth, I/O in
hot loops.

Per finding: the code path, why it's slow,
rough magnitude, the fix.
Write docs/review/performance.md.

Say which ones you'd need to profile to
confirm instead of asserting them.
```

**4. UI/UX**
```
Read-only review of the UI layer.

Cover: missing loading/empty/error states,
inconsistent components doing the same job,
forms with no validation feedback, focus
order and keyboard traps, contrast, touch
targets, destructive actions with no
confirm, flows that leave the user unsure
whether something worked.

Write docs/review/uiux.md with file:line
and the concrete change. Rank by traffic
on the affected path.
```

**5. Features**
```
Read @README.md and the codebase, then
propose features.

Context: <who uses this, what they do with
it, what they complain about, what's
already on the roadmap>.

Per idea: the user problem, why this
codebase is positioned for it, rough
implementation shape, effort. Rank by
value-to-effort.

Flag anything already half-built. No
generic ideas — ground each one in
something you saw in the code.
```
