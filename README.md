# rjWebApp

Personal portfolio and web application for Rajeev Jasti ([rjasti.com](https://rjasti.com)).

Two deployable tiers live in this repository:

- **`frontend/`** — a static, framework-free single-page site and installable PWA:
  hash-routed sections, an interactive command prompt, a live session-activity
  dashboard, an AI chat surface, and a full account UI (register, login, 2FA,
  magic links, password reset, session management).
- **`server/`** — an optional FastAPI service (`rjWebApp API`, v2.0.0) providing
  JWT authentication, anonymous activity ingest and streaming, and Amazon
  Bedrock–backed chat with conversation persistence.

The frontend runs standalone. Every backend-dependent feature degrades quietly
when the API is unreachable, so the portfolio itself never depends on it.

## Tech stack

| Tier | Technologies |
| :--- | :--- |
| Frontend | HTML5, vanilla CSS (no preprocessor/framework), ES modules, 2D-canvas backgrounds, service worker, Web App Manifest, DOMPurify, marked |
| Build | esbuild (bundling, minification, content hashing) via `scripts/build.mjs` |
| Backend | FastAPI, Pydantic v2, SQLAlchemy 2 (async) + asyncpg, Alembic, boto3/Amazon Bedrock, structlog, aiokafka, aiosmtplib, httpx |
| Auth | PyJWT (HS256), passlib + bcrypt, pyotp (TOTP), qrcode, Have I Been Pwned range API |
| Database | PostgreSQL (SQLite + aiosqlite in the test harness) |
| Tooling | Node.js test runner + jsdom, ESLint, Stylelint, Prettier, pytest, pytest-asyncio, pytest-cov, ruff |
| CI/CD | GitHub Actions → rsync/SSH to EC2 (Apache for static, systemd + Uvicorn for the API) |

No Three.js, React, Vue, Tailwind, or CSS preprocessor is used anywhere. The
`frontend/three-bg.js` filename is historical — it is a plain 2D-canvas
renderer.

## Prerequisites

| Requirement | Notes |
| :--- | :--- |
| Node.js ≥ 18 | Declared in `package.json` `engines`; CI uses 18 |
| npm | `npm ci` is used by CI and the deploy |
| Python 3.10+ | CI runs the backend suite on 3.10 **and** 3.12 |
| PostgreSQL | Required for the API; CI's migration job uses `postgres:16` |
| AWS credentials | Only for chat/model endpoints; must permit `bedrock` and `bedrock-runtime` |
| SMTP relay | Optional; only for password-reset and magic-link email |

Kafka is **optional**. With no broker configured the ingest pipeline runs in
simulated mode and browser events still reach PostgreSQL through
`POST /events/bulk`.

## Quick start

### 1. Install dependencies

```bash
npm install

# Runtime only (what the production host installs):
python -m pip install --require-hashes -r server/requirements.txt

# Runtime + test/lint tooling (what CI installs):
python -m pip install --require-hashes -r server/requirements-dev.txt
```

`requirements.txt` and `requirements-dev.txt` are **generated** locks: every
package is pinned to an exact version with hashes, so CI, your machine and the
production host install byte-identical dependencies. Never edit them by hand.

To add or upgrade a dependency, edit `server/requirements.in` (or
`server/requirements-dev.in`) and regenerate **both**:

```bash
uv pip compile server/requirements.in --universal \
  --python-version 3.10 --generate-hashes -o server/requirements.txt
uv pip compile server/requirements-dev.in --universal \
  --python-version 3.10 --generate-hashes -o server/requirements-dev.txt
```

`--universal` is load-bearing: it emits environment markers so one lock covers
every interpreter from 3.10 up. A single-version resolve pins conditional
packages unconditionally and breaks the moment CI and the host disagree on the
Python version. `tests/backend/unit/test_dependency_locks.py` enforces this.

### 2. Configure the environment

Copy `.env.example` to `.env` in the repository root and fill in the four
required values:

```bash
cp .env.example .env
```

```dotenv
DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/rjwebapp
AWS_REGION=us-east-1
DEFAULT_MODEL_ID=us.anthropic.claude-3-5-sonnet-20241022-v2:0
JWT_SECRET=<openssl rand -hex 32>
```

`JWT_SECRET` has **no fallback**. The app refuses to start if it is unset,
shorter than 32 characters, or set to the placeholder that once shipped in this
repository. See `docs/CONFIGURATION.md` for the complete variable reference.

### 3. Apply database migrations

```bash
cd server && PYTHONPATH=.. alembic upgrade head
```

`server/alembic/env.py` loads `.env` itself via python-dotenv and reads only
`DATABASE_URL`, so migrations run without Bedrock or JWT configuration.

### 4. Run the API

```bash
python -m uvicorn server.main:app --reload      # http://localhost:8000
```

Interactive OpenAPI docs are at `http://localhost:8000/docs`.

### 5. Run the frontend

Serve `frontend/` as the document root so absolute paths (`/sw.js`,
`start_url: "/"`) and normal browser security rules apply:

```bash
python -m http.server 8080 --directory frontend   # http://localhost:8080
```

On `localhost` / `127.0.0.1` the frontend targets `http://localhost:8000`
automatically and falls back to the production API if the local health check
fails (`frontend/js/analytics.js`). No edit is required to develop locally.

## Configuration

Four variables are required (`DATABASE_URL`, `AWS_REGION`, `DEFAULT_MODEL_ID`,
`JWT_SECRET`); roughly thirty more are optional and cover CORS, proxies, rate
limits, Bedrock tuning, the ingest pipeline, SSE behaviour and SMTP.

**→ Complete reference: [`docs/CONFIGURATION.md`](docs/CONFIGURATION.md)**

The frontend needs no build-time configuration. `getApiBaseUrl()` in
`frontend/js/analytics.js` selects the API base from `window.location.hostname`:

| Hostname | API base |
| :--- | :--- |
| `localhost`, `127.0.0.1`, `[::1]` | `http://localhost:8000` (falls back to production on a failed health check) |
| contains `staging` | `https://staging-api.rjasti.com/api` |
| contains `www.` | `https://www.rjasti.com/api` |
| anything else | `https://rjasti.com/api` |

## npm scripts

```bash
npm run build         # Build the optimised site into dist/ (what the deploy ships)
npm run lint          # JavaScript + CSS linters
npm run lint:js       # ESLint over frontend/*.js, frontend/js/*.js, frontend/js/terminal/*.js
npm run lint:css      # Stylelint over frontend/**/*.css
npm run format        # Prettier write
npm run format:check  # Prettier check
npm test              # Node test runner over frontend/tests/*.test.js
npm run audit         # npm audit --audit-level=high
npm run check:csp     # Verify index.html inline scripts match their CSP sha256 hashes
```

> **Never run `npm run format` on `frontend/index.html`.** Its two inline
> scripts are pinned by `sha256-` hashes in the page's CSP; reformatting one
> invalidates the hash and the browser then refuses to run it *silently*. The
> file is in `.prettierignore`, and `scripts/check_csp_hashes.py` guards it in CI.

## Testing

```bash
npm test                                    # Frontend (Node test runner + jsdom)
PYTHONPATH=. pytest                         # Backend (pytest; pytest.ini sets testpaths)
PYTHONPATH=. pytest --cov=server --cov-report=term-missing --cov-fail-under=55
ruff check server tests                     # Backend lint
```

`tests/backend/conftest.py` injects `TESTING=true` plus throwaway values for
`DATABASE_URL` (in-memory SQLite), `AWS_REGION`, `DEFAULT_MODEL_ID` and
`JWT_SECRET`, so the suite bypasses rate limiting and the import-time
configuration checks. `PYTHONPATH` must include the repository root.

**→ Details: [`docs/TESTING.md`](docs/TESTING.md)**

## Build and deploy

`npm run build` produces `dist/` — bundled, minified, content-hashed, with a
generated service-worker precache list. `frontend/` remains the source of truth
and stays runnable on its own; the build only ever reads from it.

`.github/workflows/deploy.yml` runs three quality gates in parallel
(frontend lint/test/build/CSP, backend lint/pytest on Python 3.10 and 3.12,
and migrations + `alembic check` drift detection against a real PostgreSQL),
then — only on a push to `main` — snapshots the current release, rsyncs
`dist/` to Apache's document root and `server/` to the API host, installs the
hash-pinned lock, runs `alembic upgrade head`, restarts systemd units, probes
`/api/health`, smoke-tests the deployed site, and rolls back automatically on
any failure.

**→ Details: [`docs/OPERATIONS.md`](docs/OPERATIONS.md)**

## Maintenance helpers

All scripts live in `scripts/` and are maintenance steps, not part of the build.

| Script | Purpose | Requires |
| :--- | :--- | :--- |
| `build.mjs` | Produce `dist/` (invoked by `npm run build`) | esbuild |
| `check_csp_hashes.py` | Verify inline `<script>` bodies against the CSP hashes | stdlib only |
| `vendor_fonts.py` | Re-subset and re-vendor Plus Jakarta Sans + Font Awesome | `fonttools[woff]`, network, `@fortawesome/fontawesome-free` |
| `optimize_images.py` | Recompress icons/profile images, with timestamped backups under `backups/` | Pillow |
| `verify_images.py` | Report dimensions and sizes of the optimised images | Pillow |
| `generate_profile_pics.py` | Regenerate 160/360/725-wide JPEG + WebP profile variants | Pillow |

Fonts are self-hosted and subset so no third-party origin sits in the critical
rendering path. `frontend/fonts.css` and `frontend/fonts/` are generated —
after adding an icon that is not already used anywhere, re-run:

```bash
python -m pip install "fonttools[woff]"
python scripts/vendor_fonts.py
```

`frontend/vendor/` holds DOMPurify and marked, copied verbatim from the npm
packages pinned in `package.json`. See `frontend/vendor/README.md` to update.
